# Runtime stage assumed rosdep was ready

## Overview

The headless runtime image failed in two consecutive GitHub Actions runs. Both
failures happened before runtime inspection and before the Gazebo/MoveIt smoke test.

The first run showed that `runtime-deps` did not contain the `rosdep` executable.
The first correction installed the executable, but the second run showed that
rosdep had not been initialized.

## Impact

The clean workspace build and registered ament tests passed in both runs. Each
workflow then stopped while building `runtime-headless`.

The runtime image was not created. Runtime inspection and the headless smoke test
did not run.

## Evidence

GitHub Actions run `30566668383` reported:

```text
[runtime-deps 6/6] RUN ... rosdep update --rosdistro jazzy ...
/bin/bash: line 1: rosdep: command not found
exit code: 127
```

Exit code `127` means the shell could not find the requested command.

After `python3-rosdep` was installed, GitHub Actions run `30568944356` reported:

```text
ERROR: no sources directory exists on the system meaning rosdep has not yet been initialized.
Please initialize your rosdep with

    sudo rosdep init
```

The executable check passed. `rosdep update` then returned exit code `1` because
`/etc/ros/rosdep/sources.list.d/20-default.list` did not exist.

## Root cause

`python3-rosdep` was installed in the `build-deps` stage. The workspace build and
tests inherited from that stage, so they could use an already initialized rosdep.

`runtime-deps` deliberately starts again from `ros:jazzy-ros-core-noble`. A new
Docker stage inherits only from the image named in its own `FROM` instruction. It
does not inherit packages or generated configuration from an unrelated stage.

The runtime stage copied the four `package.xml` files and called `rosdep`, but it
provided neither the executable nor rosdep's initialized source configuration.

The first correction treated executable availability as the complete requirement.
Installing `python3-rosdep` creates `/usr/bin/rosdep`, but it does not create the
system source list used by `rosdep update`. That file is generated by `rosdep init`
and is not owned by the Debian package.

The complete requirement is:

```text
rosdep package
  → rosdep executable
  → initialized source configuration
  → updated dependency database
```

## Why earlier checks passed

The `workspace-builder` and `test` stages both inherit from `build-deps`.
`build-deps` starts from `ros:jazzy-ros-base-noble`, which provides rosdep and its
source configuration. Dependency resolution, compilation, and registered ament
tests therefore passed.

`runtime-deps` is a separate branch of the Docker build graph. It starts from the
smaller `ros:jazzy-ros-core-noble` base. The first missing requirement was reached
only when GitHub built the `runtime-headless` target.

The first correction added `command -v rosdep`. That check proved only that the
executable existed. It could not prove that the tool was initialized, so it passed
before `rosdep update` reported the missing source directory.

The development container could not expose either runtime-base assumption. It has
rosdep and other development tools installed. Docker and Buildx were unavailable
inside the development container, so GitHub provided the first complete build of
each corrected runtime stage.

## Fix

The `runtime-deps` stage now:

1. installs `python3-rosdep`;
2. verifies that the `rosdep` executable is available;
3. runs `rosdep init` when the system source list is absent;
4. verifies that the generated source list exists;
5. updates rosdep and installs only dependencies of type `exec`;
6. purges `python3-rosdep`;
7. removes packages that became unused after the purge;
8. removes the system source configuration, root cache, and temporary manifests;
9. verifies that the executable and generated rosdep state are absent.

All of this happens in one Docker layer. The resolved application dependencies
remain, while the dependency-resolution tool and its generated state do not remain
in the delivered image.

The finished runtime image is checked a second time by the workflow. Runtime-image
inspection fails if `rosdep`, the temporary `sudo` dependency, or the generated
system rosdep configuration remains.

## Prevention

Each Docker stage owns every command it executes and the state required by that
command. When a stage starts with a new `FROM`, its base image and the instructions
inside that stage are its complete environment. Commands and generated
configuration from an unrelated stage are not available.

For temporary build tools in a runtime stage, install, initialize, use, and remove
the tool in the same `RUN` instruction. Verify executable availability and required
initialization before use. Check the executable and generated state after removal.

The workflow then checks the finished image independently. This gives the boundary
two protections:

- the Dockerfile proves the temporary tool's complete lifecycle while creating the
  layer; and
- runtime inspection proves the delivered image does not expose the tool or its
  generated configuration.

Future stages must follow the same rule for commands not guaranteed by their own
base image. This catches an incomplete stage contract where the assumption is made
instead of during a later container run.

## Verification

The two GitHub logs establish both missing parts of the original stage contract.
Local inspection confirms that `python3-rosdep` is installed and initialized before
use, then its executable and generated state are removed and checked before the
layer completes.

The corrected runtime image build, absence checks, and full headless smoke test
remain pending the next GitHub Actions run.
